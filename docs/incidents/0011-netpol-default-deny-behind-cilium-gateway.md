# 0011: Default-deny NetworkPolicies behind a Cilium Gateway listener

**Symptom.** Minutes after a deploy that introduced namespace-scoped
default-deny NetworkPolicies: `FluxKustomizationHealthcheckfailed` on
`cvgen-migrations` (`timeout waiting for: Job ... status: 'InProgress'`),
`CanaryRollback` fired for the gateway, the migration pod hung with an
*empty* log, `gateway-primary` went 0/1, and — found only during
investigation — **WAL archiving had silently frozen**
(`pg_stat_archiver.archived_count` stuck), degrading the brand-new PITR
backup window. Public traffic 503'd through the envoy listener.

**Investigation.**
1. The pod table was the giveaway: the migration job pod `Running` for
   minutes with an *empty* log = a TCP connect hanging, not an error.
   The primary gateway's readiness failures split into two eras — first
   `context deadline exceeded` (hangs), then fast `503`s.
2. The NetworkPolicy inventory landed exactly when everything broke.
   But the policies' client-side selectors all matched the live pod
   labels (`app=` on services, `cnpg.io/cluster=` on the database,
   chart labels on NATS, `batch.kubernetes.io/job-name=` on job pods).
   Client-side egress was never the problem.
3. **The missing half:** NetworkPolicy needs *both directions*. The set
   enforced a full client-side **egress** matrix but contained no
   server-side **ingress** allows for valkey (:6379), NATS (:4222) or
   Postgres (:5432) — so `default-deny ingress{}` dropped every
   connection *to* them. Worse, the database pod itself sat inside
   default-deny **egress** with no allow: barman could no longer reach
   S3, which is why backups froze without anyone looking at the network.
4. Even after adding the ingress allows and CNPG egress, requests
   entering through the Gateway-API listener still got `HTTP 403` with
   body `Access denied` — generated by **envoy itself**, label-
   independent, persisting after deleting the default-deny policy, and
   vanishing instantly when *all* NetworkPolicies were removed.

**Root cause.** Two stacked mistakes:
1. **One-directional policy design.** Default-deny + an egress-only allow
   matrix ignores that every allowed flow also needs the server side of
   the same contract, and that infrastructure pods (the database!) are
   clients too — its backup/WAL-archive egress is part of the dependency
   graph.
2. **Enforcement point changes the semantics.** For traffic entering
   through a Cilium Gateway API listener, the backend pods' ingress
   policies are evaluated *inside envoy as an RBAC filter*, where the
   blanket deny-all entry shadows narrower port-scoped allows — unlike
   direct pod-IP paths, which use plain eBPF L3/L4 union semantics.
   Vanilla NetworkPolicy cannot express "allow this properly behind the
   listener"; the correct tool is a CiliumNetworkPolicy using
   `fromEntities` for the host-network envoy path.

**Fix.**
- Immediate: reverted the whole NetworkPolicy commit set (service
  restored within one reconcile — public 200, primary Ready, WAL
  archiving resumed), suspended the just-landed synthetic CronJob until
  its path was understood, and bumped the documented
  `cvgen.dev/rollout-nonce` annotation to force a fresh gateway canary
  under clean networking (the previous attempt's `Failed` status would
  otherwise block retry — see incident [0010](0010-alerting-saga.md),
  10e).
- The canary then promoted cleanly, and the synthetic probe passed
  end-to-end through production once re-enabled.

**Lesson.**
1. Default-deny is a *bidirectional* contract: design the server-side
   ingress allows together with the client-side egress matrix, and treat
   infrastructure pods (databases and their backup paths) as first-class
   entries in the dependency graph.
2. With Cilium, the enforcement point depends on the traffic path —
   direct-to-pod flows follow classic union semantics, but anything
   entering through a Gateway listener is judged by envoy RBAC where an
   explicit deny shadows allows. Test policies against the *live*
   cluster through the real entry path before letting default-deny land;
   have the revert ready (here: a single git revert restored service in
   one reconcile).
